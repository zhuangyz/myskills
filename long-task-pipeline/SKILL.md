# 长任务流水线

一套把「大目标」转成「可执行长任务」的流程。核心不是写文档，而是**让一个 Agent 会话（或父 Agent + 多个 subagent）能不知疲倦地把事情做完，并且中途断线还能接着做**。

## 0. 先判断：这个任务能不能被"执行"

一个长任务能被持续执行，必须同时满足 5 个条件，缺一个就会在中途塌方：

| 条件 | 含义 | 不满足的后果 |
| --- | --- | --- |
| 真源唯一 | 设计/需求有唯一入口（节点 ID、链接、文件路径、接口文档），**执行时现场读取** | 执行者凭历史记忆和转录文本开工，越做越偏 |
| 粒度可交付 | 每个任务产出可独立验收的单元（一个页面 / 一个模块 / 一个接口） | 任务太大无法验收，太小管理成本爆炸 |
| 依赖显式 | 顺序和前置条件写在编排器里 | 执行者靠猜，乱序改文件 |
| 验收可判定 | 每个任务有通过门槛和失败留页规则 | "做完了"无法判断，返修无边界 |
| 状态可恢复 | 任务状态与运行状态落盘 | 一次断线/换会话就得从头来 |

**其中"真源唯一"和"状态可恢复"是这套流程区别于普通任务拆分的关键**，其余拆分方法论都建立在这两条之上。

## 1. 流水线总览

| 阶段 | 产出 | 门禁（不过不许进下一阶段） |
| --- | --- | --- |
| P0 侦察 | 无（内部） | 读过项目规范、目录结构、命名约定、既有变更文档格式、相关模块现状 |
| P1 定范围与真源 | 边界声明 + 真源清单 | 每个真源有稳定标识；范围外项已单列；缺口已标记 |
| P2 开发计划 | `01-开发计划.md` | 范围、边界、缺口、依赖、验收口径齐全 |
| P3 任务拆分 | `tasks/T01-*.md` … | 一个界面/模块一个任务；任务数 = 真源数（或差异有说明） |
| P4 任务编排器 | `02-任务编排器.md` | 每个任务有依赖、状态、通过门槛、阻塞条件 |
| P5 状态路由 | `03-流程与状态路由.md` | 每个按钮有去向，每个状态有唯一落点 |
| P6 多 Agent 执行器 | `04-多Agent任务执行器.md` | 启动指令、任务单、回报、返修、验收、并发规则齐全 |
| P7 执行恢复检查点 | `05-执行恢复检查点.md` | 检查点字段、租约规则、恢复步骤、幂等规则齐全 |
| P8 执行与收口 | 代码 + 集成验收 + 变更日志 | 全部任务终态；有最终交付说明（已完成/未完成） |

> 小任务可裁剪：只用 P2 + P3（+ P4）。但只要预计超过一个会话、或要交给 subagent，就不要裁 P6/P7。

**每进入一个阶段，先声明"完成标准"**（一句话说清这一轮做完长什么样），再动手。这是全程最省事的习惯。

## 2. 铁律

1. **先侦察，再动笔。** 读项目目录结构、开发规范、既有同类文档格式、目标模块现状。文档要长成项目里已有的样子，而不是你习惯的样子。
2. **一个界面 / 一个模块 = 一个任务。** 弹窗、抽屉这类浮层是独立任务（独立 widget/组件），不要塞进宿主页面任务里。
3. **同一界面的不同状态不是不同页面。** 空态/完成态、成功态/失败态属于**同一个 Page、同一个路由、同一个 ViewModel/Cubit**，靠内部状态切换；多张设计稿只作为各状态的视觉依据。这条几乎每次都会被用户纠正一次——一开始就按这个拆。
4. **不落盘设计转录，临时资源不进文档。** 只保留真源标识并要求现场读取；设计工具返回的临时下载链接（约 7 天失效）绝不写进文档，改由任务把真实资源下载进项目资源目录。
5. **缺口不编造。** 流程要求但设计稿里没有的页面/弹窗，写成"实现阻塞项"并列出，不要自己设计一个。
6. **范围边界先声明。** "只做样式"还是"同时接接口/原生 SDK"必须写死；未确认的能力单列为后续任务，不在本次任务里默默开工。
7. **只写文档就只写文档。** 计划阶段不要顺手改代码，也不要顺手改架构；有架构疑问写进文档待确认。
8. **不做"同一件事两套判断"。** 页面跳转和登录恢复、按钮行为和状态兜底，必须共用同一份状态定义（必要时补项目领域术语表 `CONTEXT.md`）。
9. **命名/编号变更要全局清理。** 合并任务、改类名后，旧类名、旧路由名、旧任务文件、旧计数（"10 个界面"）必须一次性扫干净——用 `rg` 反查旧词，一条都不留。
10. **改完必自检。** 每轮结束跑门禁（见 §7），并写一条变更日志；被中断的轮次要在下一轮补齐"交付说明"。

## 3. 各阶段怎么做

### P0 侦察
- 目录结构、开发规范、模块分层规范、领域术语表、既有同类文档（照着它的章节结构写）。
- 目标模块现状：已有页面、路由注册方式、ViewModel 组织方式、可复用组件、资源目录。
- 工作区状态：`git status --short`。**记录基线**——会话开始前用户已有的未提交改动，后续全程不许碰。

### P1 定范围与真源
- 把每个真源编号并绑定稳定标识（设计稿 → `fileKey + nodeId + 链接`；需求 → 文档路径+章节）。
- 明确本次"做/不做"清单。典型边界：样式 vs 接口 vs 原生能力。
- 列出缺口：流程里有、设计里没有的东西。

### P2 开发计划
用 `templates/01-开发计划.md`。必须回答：目标、范围、**非目标**、真源清单、页面/模块清单与边界、依赖与前置条件、验收口径、缺口与阻塞项、后续任务。

### P3 任务拆分
用 `templates/06-任务卡.md`，每个任务一张卡。卡片必须**自包含**：subagent 不继承父会话上下文，卡里没写的信息等于不存在。
- 设计入口只写链接 + 节点 ID，写清"必须现场用工具读取"。
- 多状态页面写清"一次读取全部状态节点"。
- 写清"不做的事"，防止执行者顺手扩范围。

### P4 任务编排器
用 `templates/02-任务编排器.md`。核心是一张任务表 + 状态机 + 通过门槛 + 阻塞条件。
状态枚举固定：`未开始 / 待执行 / 进行中 / 已完成 / 阻塞 / 失败待返修`。
阻塞条件必须区分：**业务阻塞**（要用户确认，允许停）vs **技术阻塞**（自己想办法，不允许停）。

### P5 状态路由
用 `templates/03-流程与状态路由.md`。把页面/模块按业务流程图串起来：
- 主链路一行写完：`入口 → A → B → C → 成功/失败`。
- 每个按钮/触发器都有明确去向，禁止"待定"。
- 每个状态（未开始/进行中/失败/成功/受限…）有唯一落点页面。
- 每个任务补上"入口、出口、失败留页、恢复规则"，并同步回任务卡和编排器。

### P6 多 Agent 执行器
用 `templates/04-多Agent任务执行器.md`。见 §5。

### P7 执行恢复检查点
用 `templates/05-执行恢复检查点.md`。见 §6。

## 4. 文档体系与命名

目录：`CHANGELOGS/<YYYYMM>/<主题>/`

```text
CHANGELOGS/202609/真人认证/
├── 01-开发计划.md
├── 02-任务编排器.md
├── 03-流程与状态路由.md          # 若已有项目流程图文档，直接引用它，不要重写
├── 04-多Agent任务执行器.md        # 编号随实际情况排，关键是"计划→卡片→编排→执行→恢复"顺序可读
├── 05-执行恢复检查点.md
└── tasks/
    ├── T01-真人认证收起页.md
    └── …
```

规则：
- **文档一律编号 + 稳定文件名**，跨文档用相对链接互相引用（`[任务编排器](02-任务编排器.md)`），便于机械校验。
- **不落盘设计转录。** 任务只保留真源标识（`fileKey + nodeId` + 链接）与"必须现场读取"的要求，**不生成规格快照**：转录会与设计稿脱节，而信息密度不足的转录会让执行者以为自己拿到了完整依据。真源读不到就是阻塞。
- 项目若已有变更日志目录（如 `AICodingChangeLogs/<日期>/<时间>.md`），每轮改完补一条。

## 5. 执行协议（父 Agent + subagent）

启动指令（用户可直接复制）：

```text
按照 <路径>/04-多Agent任务执行器.md 执行 <主题> T01–T0N。

你是父 Agent，只负责任务编排、状态管理、验收和阻塞处理。每个开发任务必须交给 subagent 完成。
一次只运行一个会修改工作区的开发 subagent。
从 02-任务编排器.md 中第一个依赖已满足的"待执行"任务开始，持续执行到所有任务完成或出现必须由
用户确认的阻塞。不要在完成单个任务后结束整个会话。
```

职责划分：

| 角色 | 做 | 不做 |
| --- | --- | --- |
| 父 Agent | 维护状态表、下发任务单、验收、返修派发、阻塞升级、集成验收派发、最终收口 | 不自己写业务代码 |
| 开发 subagent | 按任务单实现、自检、按格式回报 | 不越界改其他任务的产物，不自行扩范围 |
| 集成验收 subagent | 全部任务完成后只读复核：跨任务一致性、真源比对、启动/回归 | 不修代码 |

关键规则：

1. **`fork_turns: "none"`**：所有开发与验收 subagent 不继承父会话历史，只接收完整任务单，自行读仓库文档与真源。上下文独立、**工作区共享**——所以才必须串行写。
2. **单写入队列**：同一时间只允许一个会改工作区的 subagent。只读 subagent（复核、检索）可与写入者并行。
3. **任务单必须完整**：目标、真源标识、依赖、实现范围、涉及文件、接口/回调预留、验收项、非目标、回报格式、工作区基线（"只允许改哪些文件"）。
4. **回报必须结构化**：状态（完成/阻塞/失败）、改动文件、自检命令与结果、真源读取记录（实际读了哪些节点）、遗留问题、下一步。
5. **返修走原 subagent**：验收失败时把不合格项交回**原 subagent** 修复（它有上下文），不要新起一个从头理解。
6. **集成验收独立**：全部任务完成后由独立只读 subagent 做一次跨任务验收（流程串通、命名一致、无残留旧引用、关键路径可运行）。
7. **不可用即阻塞**：真源读不到、信息不足、依赖缺失 → 标记阻塞并说明原因，**禁止用历史输出或本地转录代替现场读取**。

## 6. 中断与恢复协议

**把"任务状态"和"运行状态"分开持久化**：任务状态在编排器的任务表里；运行状态在检查点文件里。断线后不依赖任何会话记忆。

检查点字段（写入 `05-执行恢复检查点.md`）：

| 字段 | 用途 |
| --- | --- |
| 当前任务 / 运行编号 | 定位到具体一次执行 |
| 所有权令牌 | 标识"谁在写"，防止双写 |
| 租约截止时间 | 15 分钟；租约有效期内**不许**启动新的写入者 |
| 已完成 / 进行中 / 待执行任务 | 进度快照 |
| 工作区指纹与最后变化时间 | 判断旧 subagent 是否还在写 |
| 下一步动作 | 恢复后的第一条指令 |

中断分类与处置：

- **短暂连接失败 / 503 / 超时**：不标记任务为阻塞。恢复后先确认旧 subagent 是否仍在运行，再按检查点和实际 diff 继续。
- **租约有效** → 不启动新写入者，等待或询问。
- **租约过期且工作区已停止变化** → 把任务移交给恢复 subagent，先复核部分修改（判定归属、是否可续、是否需要回退），再继续。
- **幂等重试**：重做前先看工作区现状，已完成的步骤不重复执行；绝不重复启动第二个写入者。

恢复启动指令模板：

```text
读取 <路径>/05-执行恢复检查点.md 与 02-任务编排器.md，检查上一次执行是否完成。
先确认没有仍在运行的写入型 subagent，再根据检查点、任务状态和工作区实际 diff 决定续跑或返工。
```

**每轮结束前的收口动作**（最容易漏）：写变更日志 + 输出最终交付说明（已完成 / 未完成 / 下一步）。被中断的轮次，下一轮必须补这两件事。

## 7. 门禁检查（交付前必跑）

见 `references/门禁与检查命令.md`。至少要覆盖：

- 文档数与任务数一致、链接可达、编号连续无空号；
- 旧命名残留为零（旧类名/旧路由/旧任务文件名/旧计数）；
- 每个真源标识至少被一个任务覆盖，反之每个任务都有真源；
- 文档里没有临时资源 URL；
- `git diff --check` 无空白错误；
- 与工作区基线对比：没有误改用户已有改动。

## 8. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一张设计稿 = 一个任务，不管状态 | 任务膨胀、路由重复 | 同界面多状态合并为一个任务 |
| 把设计稿转录成本地规格文档 | 转录与设计稿脱节，执行者以为拿到了完整依据 | 只留真源标识，现场读取；读不到就阻塞 |
| 用历史转录代替现场读取 | 设计已更新，实现停留在旧版 | 真源标识 + 现场读取 + 回报中列出实际读取记录 |
| 验收标准写"看起来对" | 无法判定，返修无边界 | 按元素/状态/流程列可勾选项 |
| 一次起多个写入 subagent | 文件互相覆盖，diff 无法归属 | 单写入队列 |
| 断线后直接从"下一个任务"开始 | 双写、半成品被当成完成 | 先查检查点 + 租约 + 实际 diff |
| 合并任务后不做全局清理 | 文档自相矛盾，执行者按旧编号乱跑 | `rg` 反查旧命名，清零 |
